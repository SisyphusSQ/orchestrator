# 备份、恢复与灾难处理
[English](https://github.com/SisyphusSQ/orchestrator/wiki/EN-Backup-and-Restore) · **中文** · [Wiki 首页](https://github.com/SisyphusSQ/orchestrator/wiki/Home)

orchestrator 没有一份可以覆盖所有故障的“集群备份”。至少要分别保护 Raft 状态、每节点元数据库、配置与密钥引用、审计/恢复证据，以及被管理 MySQL 自身。Raft snapshot 不是 MySQL 数据备份，也不是元数据库备份。

## 资产与恢复目标

| 资产 | 包含内容 | 不包含内容 | 建议恢复目标 |
| --- | --- | --- | --- |
| `raft.dataDir` | 共识日志、成员身份、快照 | 节点元数据库、MySQL 数据 | 恢复同一成员身份或用于灾难取证 |
| 节点元数据库 | 已发现拓扑、别名、审计、恢复记录、页面配置 | Raft 成员关系、实时 MySQL 状态 | 重建该节点的应用状态 |
| 配置与证书 | 节点身份、地址、访问策略、凭据引用 | 凭据管理器中的秘密 | 可重复部署同一策略 |
| MySQL 备份 | 业务数据与复制恢复基础 | orchestrator 决策记录 | 数据库灾难恢复 |
| 外部 KV/路由 | 应用写入口 | MySQL 数据与 Raft 状态 | 验证 fencing 和 writer 指向 |

先定义 RPO/RTO、保留期、加密、异地副本、责任人和定期恢复演练。只验证备份任务成功而没有实际恢复，不算可用备份。

## 常规备份

1. 记录版本、commit、节点 ID、Raft configuration index、Leader、成员表和健康状态。
2. 通过 `raft-snapshot` 请求 Leader 创建快照，并确认操作返回和 snapshot 文件出现；该步骤只推进 Raft snapshot。
3. 使用对应数据库引擎的一致性方式备份每个节点元数据库。MySQL 使用受支持的逻辑/物理备份；SQLite 不能在进程写入时直接复制单个文件，使用 SQLite backup API、受控停机或一致性 snapshot。
4. 备份每节点完整 Raft 目录时，采用应用明确允许的文件系统一致性点；不要只复制 `raft.db` 或 `snapshots/`。
5. 保存脱敏配置、证书链、systemd/container 定义、代理配置和外部依赖清单。秘密应由密钥管理器单独恢复。
6. 对备份做 checksum、加密和异地复制，记录恢复所需权限。

不同一致性域的备份时间可能不同，因此恢复后必须让实时 MySQL 重新发现并校正元数据库视图。不要假设 Raft snapshot 和元数据库 dump 在事务上对齐。

## 单节点故障

如果多数派健康，首选把故障节点作为替换成员处理：

1. 确认剩余 voter 仍有多数派，流量不再送往故障节点。
2. 保留故障盘用于取证，不要立刻清空或复用其 ID。
3. 使用新的稳定 ID 和干净 Raft 目录启动替代节点，并准备独立元数据库。
4. 通过 Leader 加入替代节点，确认配置提交、状态追平和 readiness。
5. 再移除旧成员 ID；回读所有节点的配置。

只有需要原身份原地恢复且能证明 Raft 目录、`node-id` 与配置完全一致时，才恢复原成员状态。把其他成员的 Raft 目录克隆给新节点会复制身份并破坏安全边界。

## 元数据库损坏

先隔离节点并阻止其接收管理流量。恢复该节点独立元数据库，核对 Schema 版本和迁移状态，然后启动并等待拓扑重新发现。页面化恢复策略、Hook assignment、审计和 alias 可能来自元数据库，恢复旧备份会回退这些值；启用自动恢复前必须回读有效策略。

不要把另一个仍在运行节点的 SQLite 文件在线复制过来。MySQL 元数据库也不能因为“Raft 会同步”而跳过引擎级一致性备份。

## 多数派丢失

失去多数派时停止所有拓扑写入和自动恢复，不要直接改元数据库绕过 Raft。先判断是网络分区、证书/地址错误、磁盘问题还是成员永久损失，并保护所有 surviving state。

恢复优先级：恢复足够的原 voter 形成原集群多数派；确认唯一 Leader；校验成员与日志；再恢复服务流量。只有在原多数派无法恢复且已获得灾难变更授权时，才能考虑新集群重建。重建必须选定唯一权威的 MySQL/元数据库状态、重新配置成员、重新发现拓扑、重新应用页面策略，并显式 fence 旧集群，防止它重新出现形成双控制面。

## 恢复演练验收

- 在隔离网络中恢复，旧生产集群不能接收演练写流量。
- 节点身份、成员地址、configuration index 与预期一致，没有重复 ID。
- 元数据库 Schema 可用，恢复配置、Hook、alias、maintenance/downtime 和审计范围已核对。
- 对真实 MySQL 重新发现后，拓扑边、候选、GTID/坐标和只读状态正确。
- Web/API/CLI 都能读取；受控写入只执行一次并有审计证据。
- 外部 KV、代理和应用 writer 与 MySQL 实际可写主库一致。
- 记录实际 RPO/RTO、丢失数据、人工步骤和下一次改进。
